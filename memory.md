# Long-Term Memory

This file keeps durable operating memory for future Codex sessions. Prefer this over dated handoff notes when a detail affects future decisions.

## Operating Boundary

- The deciding AI session is the AI decision entry point. Either Codex or Claude fills that role for a given run; both are peer operator-facing CLI sessions.
- The extension panel and Node scripts collect data, export snapshots, validate schemas, execute APIs, verify landing, write notes, and summarize results.
- Do not add an AI provider, model runtime, or second strategy layer inside the panel.
- Action schemas must carry `approvedBy` set to `codex`, `claude`, or `manual` to clear the executable gate (see `src/ai_decision.js`).
- Developer/product requests are handled through `.codex/skills/developer-product-inquiry`; triggers are `开发诉求` or `开发`. The operator must forward the source message/screenshot, and every response must include product/window evidence, execution status, follow-up checkpoints, and a human-ready reply.
- Default operating doctrine from 2026-05-12: the AI decision session should do what it believes will improve profit, sales quality, inventory turnover, or KPI trajectory, execute the supported action, and then learn from daily data. Do not use "business risk" as a reason to park advertising actions in manual review. Instead, record the hypothesis, baseline, expected effect, measurement windows, and rollback condition; then check 1/3/7-day data and correct if the result diverges.
- `review` is no longer the default answer for uncertain advertising strategy. Use `review` only for non-advertising business decisions or unsupported execution surfaces such as price, replenishment, listing copy approval, SB create, or actions that cannot be represented as a verifiable schema. If the action is technically supported but strategically risky, approve it explicitly with `forceExecute: true` and make the learning/rollback plan explicit.
- Technical gates remain hard gates: unknown SKU/entity, out-of-scope SKU, missing required ids, missing create fields, missing verification mapping, invalid auth/session, or API writes that do not land must be reported as technical blockers or `not_landed`, not hidden behind manual review and not counted as closed-loop success.

Do not wait for perfect confidence. The learning loop is `hypothesis -> action -> landed verification -> daily data check -> attribution -> correction`. If the result misses expectation, inspect whether the hypothesis, data baseline, SKU selection, ad entity, bid/budget magnitude, season timing, listing readiness, or execution landing was wrong, then issue a corrective schema.
